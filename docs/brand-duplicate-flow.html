How a proposed brand name is judged

A single-process TypeScript pipeline that decides whether a newly proposed brand name already exists in a catalogue of 17,653 values. Every decision comes from deterministic matching rules — no language model is involved. Every step, threshold and code reference on this page was read out of the current source and, where marked, confirmed by running the real CLI.

Entry point
brand-cli.ts → checkBrand()
Catalogue source
response.json · 17,653 values
Scripts handled

Shortlist size

Decision values
BLOCK · HUMAN_REVIEW · ALLOW

What it does

The checker answers one question about one proposed name. It does not scan the catalogue for existing duplicate pairs, merge brands, write anything back, or call a cloud API.

Implemented present and reachable in the shipped CLI path Not wired code exists, never constructed by brand-cli.ts Inferred not stated in code — reasoned from structure

The problem

The same brand reaches the catalogue written many different ways: casing and punctuation (LEVI'S / LEVIS), word boundaries (Dream Baby / Dreambaby), typos (Adiddas), and — the hard case — in the other script entirely (אדידס / ADIDAS). Hebrew writes no short vowels, so a Hebrew spelling and its Latin original almost never agree letter by letter. Plain string similarity cannot bridge that gap, which is why roughly half the codebase is transliteration and phonetic machinery.

The three outcomes

DUPLICATE decision: BLOCK

The name is the same brand as one already in the catalogue. Creation should not proceed.

  • Normalized exact match (score 1.0)
  • Curated transliteration exact (≥ 0.98)
  • Approved alias Not wired
  • Safe strong typo — one edit, long name
REVIEW decision: HUMAN_REVIEW

Nothing automatic could settle the name. A person must confirm or reject it. This is the default landing place for every ambiguous cross-script pairing.

  • Strongest candidate ≥ 0.68
  • Strongest is COMPACT_EXACT or RELATED_NAME
  • Convincing cross-language evidence
NEW decision: ALLOW

No plausible duplicate. The name may be created.

  • No candidates at all (confidence 1)
  • Strongest candidate < 0.68 and no cross-language evidence
On the word “confidence”

BrandCheckResult.confidence carries two different quantities. On Block and Review it is a match score — higher means more likely a duplicate. On Allow it is headroom below the match threshold — a small number means the call was close. The terminal formatter relabels it (“Margin below a match”). The confidence figure is internal: the report file carries only ALLOW or REVIEW.

End-to-end flow

Stages 1 and 2 run once per process. Stages 3 to 7 run per proposed name.

1
Catalogue load Implemented

The raw API payload is flattened into Brand{code, label, translations[]}. Entries missing a string code or label are dropped silently.

brand-adapter.ts · parseBrandResponse() ← response.json
2
Index construction Implemented

Each brand label and every translation becomes an index entry. Twelve maps are built: normalized text, compact text, 2-char prefix, first character, bigrams, romanization exact / prefix / bigram, consonant skeleton, and two phonetic key maps. Romanizations and phonetic keys are computed once here, never per check.

brand-index.ts · BrandIndex.add()
3
Normalization Implemented

NFKC, strip invisible formatting, unify apostrophes and quotes, turn hyphens and ampersands into spaces, drop safe punctuation, collapse whitespace, lowercase. Produces normalizedText and compactText (spaces removed).

brand-normalizer.ts · normalizeBrandNameParts()
4
Same-script retrieval & scoring Implemented

Weighted retrieval builds a pool of up to 100 entries, each scored by a weighted blend of edit, bigram, token, length and prefix similarity, then classified into a match type. Top 5 returned.

candidate-generator.ts · brand-candidate-scorer.ts · string-similarity.ts
5
Cross-script retrieval & scoring Implemented

Three independent sub-paths run and their results are merged per brand: Hebrew→Latin romanization, Latin→Hebrew expansion, and phonetic alignment. A credibility filter rejects pairings that only exist because an unlikely spelling was invented.

cross-language-candidate-generator.ts · transliteration-service.ts · latin-to-hebrew-transliteration.ts · cross-script-phonetic-matcher.ts
6
Merge & reserved slots Implemented

Candidates are deduplicated by brand code keeping the highest score, sorted, and cut to 5. Two of those five slots are then guaranteed to the strongest cross-script candidates, which displace the weakest non-guaranteed entries — a Latin input could otherwise fill every slot with Latin lookalikes and push the Hebrew spelling of the same brand off the list.

brand-duplicate-checker.ts · mergeCandidates() · withCrossLanguageCandidates()
7
Deterministic decision Implemented

Seven ordered gates. The first that matches wins. Exact, curated-transliteration, alias and safe-typo gates produce Block; everything else falls through to a review test and finally to Allow.

decision-engine.ts · DecisionEngine.decide()

Decision tree

The exact order of DecisionEngine.decide(). Every gate is a deterministic rule.

1

Is there a NORMALIZED_EXACT candidate scoring ≥ 1.0?

Both names reduce to the same normalized text. Covers casing, punctuation, hyphens, ampersands, apostrophes and whitespace.

Yes → Duplicate confidence = 1.0 No → gate 2
decision-engine.ts:31–34 · config exactBlockThreshold: 1
2

Is there a COMPACT_EXACT candidate scoring ≥ 1.0? Unreachable

Compact matching removes word boundaries (Dream Baby ↔ Dreambaby). The scorer assigns COMPACT_EXACT a fixed 0.97, so the gate can never fire — compact-only matches fall through to review at gate 7. This is intentional (“surfaced but remains review-only by default”), but the condition is written as a tunable threshold when it is effectively a hard-coded never.

Always → gate 3 Review reached later at gate 7
decision-engine.ts:36–39 · brand-candidate-scorer.ts:65–72 · config compactExactBlockThreshold: 1
3

Is there a TRANSLITERATION_EXACT candidate with transliterationExact and source === "CURATED" scoring ≥ 0.98?

Three conditions must hold at once. A generated transliteration scores 0.8 + 0.19 × confidence and generated confidence caps at 0.75, giving a ceiling of 0.9425 — below 0.98. So both the source check and the score check independently restrict this gate to curated pairs: 7 hand-written in commonBrandRepresentations plus the verified brand pairs loaded from data/phonetic-transliteration-rules.json by brand-overrides.ts.

Yes → Duplicate No → gate 4
decision-engine.ts:41–52 · transliteration-service.ts:79–88, 171 · brand-candidate-scorer.ts:115
4

Is there an APPROVED_ALIAS candidate? Not wired

No score threshold — an approved alias blocks outright. Aliases are explicitly curated and never inferred. The CLI constructs no alias resolver, so this gate never fires in production.

Yes → Duplicate No → gate 5
decision-engine.ts:54–57 · brand-alias-resolver.ts · brand-cli.ts:25
5

Is the candidate list empty?

Nothing was retrieved at all — the strongest possible signal that the name is new.

Yes → New confidence = 1 No → gate 6
decision-engine.ts:59–62
6

Is the strongest candidate a safe strong typo?

All of: type is HIGH_FUZZY; edit distance exactly 1; score ≥ 0.80; equal token counts; not a prefix variant; both names longer than 3 characters; shorter name ≥ 6 characters. Short names are excluded by shortNameFuzzyBlockThreshold: 1.01 — a value above the maximum possible score, encoding “never” as an unreachable number. A replaced letter must also be typeable: when the two keys are not neighbours on the keyboard (Hebrew SI 1452 or QWERTY) and the letters do not spell one sound, the pair scores as two edits and classifies as WEAK_SIMILARITY — סטפיל is not a typo of סטייל.

Yes → Duplicate No → gate 7
decision-engine.ts:64–66, 376–401 · config strongFuzzyBlockThreshold 0.8 · shortNameMaxLength 3 · strongFuzzyMinLength 6
7

Final fall-through: is any review condition true?

Only whole-name candidates count from gate 5 on. A candidate marked partialMatch — the proposed name adds words to it (קלין לוג'יק against קלין, NIVEA MEN against NIVEA), or one word differs entirely from the word in its place (קליר דיאה against קליר דיי) — stays in the list but is skipped, as is a cross-script spelling resemblance that neither pronunciation nor the consonants confirm (סטפיל reads “stpl”, one letter from STP). Among the rest: strongest is COMPACT_EXACT or RELATED_NAME, or cross-language evidence exists, or the strongest score ≥ 0.68. Cross-language evidence means some candidate, at any rank, carries a convincing signal — an exact transliteration, a shared consonant skeleton of ≥ 5 letters, or a match confirmed by pronunciation at similarity ≥ 0.72. A spelling that merely looks alike is not evidence on its own: expanding a name into the other script reaches some unrelated brand for almost any input (HQ reached הקס at 0.60), so such a guess reviews only when it scores ≥ 0.68 itself.

Yes → Review confidence = max(strongest, evidence) No → New confidence = 1 − strongest score
decision-engine.ts:78–104, 321–334 · config reviewThreshold 0.68 · crossLanguageEvidenceThreshold 0.72 · skeletonEvidenceMinimumLength 5

The orchestrator. checkBrand(), plus candidate merging and reserved-slot logic.

Observations & potential issues

Documented, not fixed. Nothing above was reshaped to hide any of these. Severity marks the left edge: red affects decisions, amber affects correctness of reporting or configuration, grey is hygiene.

01Only curated cross-script matches can BLOCK

Gate 3 requires source === "CURATED" and score ≥ 0.98. A generated exact transliteration scores 0.8 + 0.19 × confidence, and generated confidence caps at 0.75, giving a hard ceiling of 0.9425. The two conditions are independently sufficient to close the gate. That leaves curated pairs — 7 hand-written in commonBrandRepresentations and the verified brand pairs in data/phonetic-transliteration-rules.json — as the only inputs that can produce a deterministic cross-script block.

The consequence is structural: outside the curated pairs, scoreHebrewExpansion() emits source: "GENERATED", and scorePhonetic() always sets transliterationExact: false — so the entire Latin→Hebrew direction and the entire phonetic path are capped at Review by construction, however strong the evidence.

Verified by running the CLI (2026-09-28) גוצי and טומי הילפיגר (curated in the data file) → 99% → BLOCK. ברברי → BURBERRY by pronunciation at 91% → HUMAN_REVIEW.

03Two gates encode “never” as an unreachable number

compactExactBlockThreshold: 1 is compared against a score hard-coded to 0.97, and shortNameFuzzyBlockThreshold: 1.01 sits above the maximum score any candidate can reach. Both behaviours are intentional and the comments say so, but each is written as a tunable threshold when it is really a disabled branch. Any value in (0.97, 1] behaves identically for the first; lowering the second below 1.0 silently turns on short-name fuzzy blocking.

04confidence carries two different quantities

On BLOCK and HUMAN_REVIEW it is a match score; on ALLOW it is headroom below the threshold, where a small number means a close call. The formatter relabels it for humans, but the raw confidence field — what any programmatic consumer would read — does not. Any consumer that sorts or thresholds on confidence across mixed decisions will read it backwards for allows.
